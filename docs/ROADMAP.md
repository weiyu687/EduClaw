# EduClaw 后续开发路线图与产品设计原则（最终规划版）

> 版本：v1.0 ｜ 制定日期：2026-10-10 ｜ 文档性质：产品路线图、工程约束与发布验收标准
> 状态：规划文件；“已完成”以现有测试日志为依据，尚不代表全平台安全审计完成。

## 1. 产品定位与成功标准

**定位**：EduClaw 是以自然语言为核心交互方式、兼容 `/` CLI 命令、可扩展工具生态、具备可审计权限与可靠任务执行能力的个人/团队 Agent 平台。CLI 是成熟入口之一，未来提供可视化桌面/Web 界面，但不能形成三套彼此不一致的业务逻辑。

**用户价值**：用户只需表达目标、审阅关键变更、授权必要操作、查看可信结果；任务 ID、授权 Token、检查点、工具协议、版本链等由系统管理。

**产品成功的可检验指标**（初始目标，后续依据真实用户测试校准）：

- 常见任务从创建到完成，不要求用户复制内部 Task ID、Draft ID 或 Permission Token。
- 所有主要能力均可通过自然语言和 `/` 命令完成；GUI 与两者共享同一业务 API。
- 每个高风险动作有清晰的对象、范围、后果和确认入口；不能通过模糊指令跳过安全审批。
- 失败可解释、可恢复、不可悄悄重放；执行结果和证据可追溯。
- 新增标准 MCP 工具时，原则上无需修改任务编排核心代码。
- 新用户能按照文档安装、完成示例、理解授权与恢复机制。

## 2. 当前开发基线与遗留问题

根据已有 Windows 日志，已验证的核心链路包括：PDF 提取 → JSON 步骤引用 → Python 计算；DAG 依赖；文件读取授权与 Python 执行确认；SQLite 工具结果持久化；目标验收；已完成任务重复执行拒绝；人工重规划草案审批；重规划后继承已完成 PDF 结果；当前任务无 ID 快捷命令的单元测试。Windows SQLite 文件占用问题已提供连接显式关闭修复补丁，用户反馈该轮测试结束。

**仍需系统验收的风险**：多任务歧义、跨会话/重启后的上下文恢复、审批令牌绑定和过期、重规划的真实差异、失败/不确定状态、并发与崩溃一致性、GUI 与 CLI 一致性、复杂工具 Schema、跨平台资源释放、模型误判、用户实际可理解性。现有目标验收 `passed` 不是独立事实核验。

## 3. 分阶段路线图

### Phase 5.12.3c：统一任务上下文与交互（P0）

**交付**：
- 当前会话的任务焦点、待审批操作、待确认重规划草案统一由上下文服务管理；禁止 CLI 各分支自行猜测“最近的 ID”。
- `/任务` `/状态` `/结果` `/继续` `/允许` `/拒绝` `/重规划` `/确认` `/取消` 与自然语言等价入口；保留所有旧命令及显式 ID 用法。
- 多个候选任务或授权时显示可理解的任务名称和序号，让用户选择；不能自动选取不唯一对象。
- 默认显示进度、已完成/待执行步骤、下一步操作；内部 ID、原始 JSON 和 Token 放入 `/debug`。
- 统一确认状态机：普通“继续”只能进入代码预览/授权确认，不直接触发高风险执行；重启后不会恢复可复用的明文授权 Token。

**验收**：单任务全程无 ID；双任务歧义阻断；权限拒绝和重复确认防护；旧命令回归；CLI 重启后安全恢复。

### Phase 5.12.4：真正的动态重规划与任务版本链（P0）

**交付**：
- `/重规划 第二步增加每页表格数量` 或自然语言修改任务；允许填写理由与变更目标。
- 新旧计划结构化差异：增加/删除/修改的步骤、工具、参数、依赖、权限风险和预期输出。
- 已完成步骤和不可变结果只读继承；禁止重规划已认领、执行结果不确定或已完成的操作。
- 无实际变化时提示并阻止无意义版本替换；人工确认后原任务冻结、新版本激活。
- 稳定的用户级任务编号与内部执行版本分离；审计可回溯每次计划及批准人/时间。

**验收**：PDF 已读 → 仅修改 Python 后续分析 → 不再调用 extract_pdf；无变化重规划被拒；跨版本 SHA256 不变；并发提交不重复。

### Phase 5.13：失败分类、人工恢复与长任务（P0）

**交付**：
- 失败类别：规划/语法错误、输入 Schema 错误、权限拒绝、确定性工具失败、超时与结果不确定、目标未达成。
- 任务暂停、恢复、取消和人工修复；恢复前显示“将执行什么”和“不会重放什么”。
- 崩溃/重启一致性校验、原子状态转移、幂等键、工具执行记录和补偿策略；不承诺外部工具具备天然幂等性。
- 长任务进度、取消传播、超时策略、资源上限与中断反馈。

**验收**：故障注入、断电模拟、重复提交、工具超时/结果未知均不自动重放；恢复后状态可信。

### Phase 5.14：插件化工具生态与开发者 SDK（P0/P1）

**交付**：
- 工具注册表、能力描述、输入/输出 Schema、风险等级、权限资源范围、执行适配器。
- MCP 工具动态发现；版本兼容、健康检查、隔离与禁用、失败可解释。
- 统一结构化工具结果、引用路径、大小限制、敏感信息处理和审计元数据。
- 插件模板、示例、开发文档和契约测试；核心编排不包含针对特定工具的专用业务分支。

**验收**：新增 PDF 以外的新工具，能经注册完成自然语言规划、权限审批、执行、结果引用、GUI 呈现和回归测试。

### Phase 5.15：智能规划、上下文与结果质量（P1）

**交付**：
- 模型规划输出的 Schema 校验、受控纠错与失败反馈；避免针对单一 PDF 用例硬编码。
- 工具能力匹配、DAG 合法性、预算/成本/Token 管理、上下文压缩、可解释计划。
- 目标验收区分形式合规、证据存在与独立事实正确性；必要时提示用户核查。
- 任务模板、用户偏好、可控记忆与隐私边界；禁止将工具输出视为高权限指令。

**验收**：跨 PDF、表格、网页、数据库等多类任务基准；模型异常输出时安全失败。

### Phase 5.16：安全、审计、可观测性与质量评测（P0，贯穿所有阶段）

**交付**：
- 统一审计事件：任务、版本、步骤、工具、审批、权限、结果摘要、失败与恢复。
- 威胁建模、Prompt Injection 防护、最小权限、路径规范化、秘密脱敏、日志保留策略。
- 端到端指标：任务成功率、人工干预次数、恢复成功率、重复执行次数、耗时、成本。
- CI 测试矩阵：Windows 优先，逐步扩展 Linux/macOS；数据库、文件句柄、并发、权限、升级迁移。

**验收**：能回答“谁批准、执行了什么、为什么、是否重放、证据在哪里”；异常注入不越权。

### Phase 5.17：可视化界面（GUI）与多端一致性（P1；基础设施提前启动）

**策略**：不要等后端全部完成才开始 GUI。自 Phase 5.12.3c 起抽离共享 Application Service / API；Phase 5.14 后推出可用 GUI MVP，Phase 5.17 完成产品化。

**GUI MVP 必备页面**：
1. **对话与任务首页**：自然语言输入、任务卡片、下一步操作、任务历史。
2. **任务详情与 DAG 视图**：步骤状态、依赖关系、输入输出摘要、版本差异、实时进度。
3. **审批中心**：文件/代码/外部操作审批；清楚展示资源、范围、风险、代码预览、拒绝与取消。
4. **重规划对比页**：旧计划与新计划差异、保留结果、增加权限、确认/驳回。
5. **工具与插件管理**：发现、安装/启停、权限、健康状态、版本与错误。
6. **结果与证据中心**：可读结论、表格/文件预览、引用来源、导出。
7. **设置与诊断**：模型/服务连接、隐私与数据目录、日志级别、调试信息。

**体验要求**：GUI、CLI、自然语言三入口共用同一任务服务、权限引擎和持久化状态；不允许 GUI 直接绕过审批。默认简洁，专家模式可展开原始 JSON、SHA256 和内部 ID。实时状态通过事件订阅/轮询，断线可恢复，不以页面关闭代表任务取消。

**技术选型原则**：先根据 Windows 本地部署、跨平台目标、安装包大小、维护成本和安全隔离做技术评估；桌面壳（如 Tauri/Electron）或 Web 前端不预先写死。后端优先提供稳定本地 API，明确身份认证、CSRF/CORS、端口绑定与本地访问边界。

**验收**：新用户无需阅读 CLI 帮助即可完成 PDF→Python 两步任务、审批、查看 DAG、修改未执行步骤、查看证据；键盘可操作、提示清晰、加载/失败/空状态完整；GUI 与 CLI 对同一任务状态一致。

### Phase 5.18：从头到尾的产品设计与真实用户体验审查（P0，发布门槛）

**必须作为独立阶段，而不是仅做代码测试。** 邀请不熟悉 EduClaw 内部机制的目标用户，完整走通以下旅程：

- **首次接触**：定位是否清楚、安装是否简单、首次启动/模型连接是否可理解。
- **首次成功**：示例任务是否容易完成，用户能否知道系统做了什么、为什么需要授权。
- **日常使用**：自然语言是否可靠、`/` 命令是否一致、结果是否可读、无需复制内部 ID。
- **复杂任务**：多任务切换、DAG、重规划、长任务、失败恢复、文件与多工具协作。
- **异常场景**：拒绝授权、断网、工具不可用、超时、进程崩溃、重启、数据迁移、错误输入。
- **安全与信任**：权限边界可理解，危险操作可取消，结果证据可核对，隐私与日志可控制。
- **可访问性**：键盘导航、对比度、状态不只依赖颜色、中文提示一致、适配常见屏幕尺寸。
- **维护与卸载**：升级/回滚、配置迁移、日志收集、数据导出/删除、卸载后的数据处理。

**审查方法**：任务走查、启发式评估、5–8 位目标用户的可用性测试（建议起点）、问题严重度分级、行为指标、回访复测。每个 P0/P1 产品问题必须有责任人、修复版本和复测记录。

**发布阻断条件**：存在可绕过审批、可重复执行高风险操作、丢失结果、用户无法理解关键权限、关键旅程无法完成的 P0 问题时，不进入正式发布。

### Phase 6.0：开源发布与长期维护（P1）

**交付**：README、架构与威胁模型、安装/卸载/升级、示例任务、插件 SDK、贡献指南、许可证与第三方依赖审查、CI/CD、发行包、版本兼容政策、Issue/安全漏洞反馈机制。

**验收**：全新 Windows 环境可按文档安装并完成示例；新贡献者可运行测试并开发插件；发布候选版通过产品设计复查。

## 4. 不可妥协的长期开发原则

1. **真实用户体验优先**：操作少、反馈清楚、默认隐藏实现细节；系统管理 ID/Token，不让用户背负内部复杂性。
2. **自然语言为主、`/` 命令永久并存**：每项主要功能同时具备两种入口；历史 `/` 命令不得随意删除；GUI 是第三入口，共享业务逻辑。
3. **安全默认拒绝（fail-closed）**：无授权不执行；模糊目标不猜测；高风险操作需要与具体工具/资源/参数绑定的明确审批。
4. **便利不等于绕过审批**：`/继续`、自然语言“好的”、GUI 按钮不能跳过 Python 代码预览和安全确认；重规划后的新增风险重新授权。
5. **禁止隐式重放**：已完成或结果不确定的工具调用不可自动重试；恢复必须验证状态和操作身份。
6. **结果不可变、证据可追溯**：持久化结果、SHA256、版本链、审批记录和 DAG 必须保持一致；复制结果不等于再次执行工具。
7. **低耦合、插件化、Schema 驱动**：工具能力、风险与参数由注册信息描述；任务引擎不写死具体工具逻辑。
8. **通用机制优先**：避免为单个 PDF、Excel 或测试样例硬编码；先解决抽象契约，再做特例适配。
9. **接口兼容优先**：旧 CLI、工具协议、SQLite Schema 和现有测试尽量保持兼容；迁移要可回滚。
10. **状态机与事务明确**：审批、认领、执行、完成、失败、取消、重规划、恢复均有合法转移；持久化使用原子事务。
11. **资源生命周期可靠**：数据库连接、文件句柄、子进程、临时目录和网络连接显式释放，重点覆盖 Windows `WinError 32`。
12. **不夸大验证结果**：区分单元测试、集成测试、Windows 实机、GUI 体验测试和安全审计；目标验收通过不代表事实必然正确。
13. **隐私与最小数据原则**：敏感文件、日志、模型上下文、工具结果按需使用；提供清晰的数据保留和删除机制。
14. **可观察、可解释、可维护**：错误面向用户提供行动建议；专家模式保留足够审计信息；关键决策可复盘。
15. **每次增量可交付**：小范围补丁、版本说明、测试命令、回归清单、回滚办法；避免一次性大改。
16. **真实用户测试决定优先级**：优先修复阻碍任务完成和理解的体验问题，而非单纯堆砌功能。

## 5. 工程架构约束

```text
自然语言 / CLI / GUI
        │
统一意图与任务上下文层（解析、歧义消解、用户级任务编号）
        │
Application Service / 统一任务 API
        │
任务编排（Plan / DAG / Replan / Goal / Recovery）
        │
安全策略与审批引擎（统一权限、风险、审计）
        │
工具注册表与执行适配器（MCP / 插件 / 执行沙箱）
        │
SQLite 状态 / 不可变结果 / 事件与审计日志
```

**分层边界**：交互层不得直接调用高风险工具；GUI 不直接修改 SQLite；模型生成的计划必须经过确定性 Schema/DAG/权限校验；工具返回的数据视为不可信输入；同一业务操作只有一个实现路径。

## 6. 每阶段 Definition of Done（交付完成定义）

- [ ] 有明确用户故事、交互样例和可验证验收条件。
- [ ] 自然语言、`/` 命令等价；若已有 GUI，则 GUI 也同步支持。
- [ ] 旧命令、旧数据和已存在任务流程的兼容性经过验证。
- [ ] 权限拒绝、歧义阻断、重复审批、结果不确定、防重放测试通过。
- [ ] SQLite 事务、连接关闭、Windows 临时目录与文件句柄测试通过。
- [ ] 新增单元测试、集成测试及关键端到端回归通过。
- [ ] UI/CLI 的成功、加载、空状态、失败、取消、恢复反馈完整。
- [ ] 提供补丁/安装说明、数据库迁移和回滚步骤。
- [ ] 说明已验证范围、未验证风险与后续问题，不将局部通过说成全面通过。
- [ ] 用户实际操作走查通过，发现的问题有记录与优先级。

## 7. 建议的近期执行顺序

| 顺序 | 工作包 | 关键交付 | 主要依赖 |
|---|---|---|---|
| 1 | 5.12.3c 统一任务交互 | 无 ID 操作、歧义消解、双入口、统一审批上下文 | 当前 5.12.3b |
| 2 | GUI 基础架构 Spike | 共享任务 API、事件模型、界面原型、技术选型记录 | 5.12.3c 并行 |
| 3 | 5.12.4 动态重规划 | 修改要求、差异对比、版本链、人工确认 | 5.12.3c |

| 6 | GUI MVP | 任务首页、审批、DAG、重规划、结果中心 | 共享 API + 核心状态机 |
| 7 | 5.15 智能决策 | 规划质量、工具选择、证据评估 | 工具 Schema |

## 8. 版本维护约定

此文档作为后续开发的统一规划基线。每完成一个 Phase，更新：实现范围、测试证据、未解决风险、接口变化、产品反馈和下一阶段优先级。涉及权限、不可变结果、旧命令兼容和用户体验原则的变更，应先记录设计理由与风险，再实施代码修改。
